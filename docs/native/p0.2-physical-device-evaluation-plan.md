## Evidence boundary

The repository previously proved that the paired iPhone can accept and launch a signed native build. That connectivity evidence does **not** prove that the Qwen diagnostic package loads, translates, meets latency/memory budgets, stays thermally acceptable, or works offline on the phone.

Issue #108 therefore commits the measurement contract before the physical run. Simulator/macOS results must keep `physicalDeviceEvidence.state = notRun`; only issue #109 may replace that state with physical-device observations.

## Runtime measurements

The pinned MLX Swift LM API exposes completion information through `ChatSession.streamDetails`. The benchmark records these values directly rather than inferring them:

- whether the model container load was cold;
- cold model-load duration measured with a monotonic clock;
- prompt/first-token duration after the model container is ready;
- generation duration;
- prompt-token count;
- generated-token count;
- generated tokens/second;
- stop reason (`stop`, `length`, or `cancelled`).

A warm case reuses the loaded model container but still creates a fresh `ChatSession`, so transcript/KV state is not reused across fixtures. A max-token stop is classified as truncated output.

Metrics unavailable because a case failed before completion stay `null` and are listed in `unknownMeasurements`. A missing measurement is never estimated from model size, wall-clock impressions, or another platform.

## Predeclared performance screening budget

These are screening targets for the candidate decision, not claims that Qwen currently meets them:

| Measurement | Budget |
| --- | ---: |
| Cold model load | <= 8.0 s |
| Warm first token after model ready | <= 1.5 s |
| Warm generation | <= 4.0 s per fixture |
| Warm generation throughput | >= 10 tokens/s |
| Peak resident memory | <= 1.5 GiB |
| Thermal state during one full pass | must not reach `serious` or `critical` |
| Offline after provisioning | must pass |
| Cancellation | must pass |

The latency targets are deliberately chat-oriented screening thresholds: a fallback that routinely stalls for many seconds after every message is not a useful interactive translation route even if its translations are correct. The memory threshold leaves material headroom on the currently paired high-end iPhone instead of treating the 335 MB weight file as resident-memory evidence.

Battery level/charging state is recorded before and after the full synthetic pass but is observational rather than a hard percentage gate. A short run is too coarse for a reliable battery-percentage threshold; repeated energy profiling can be added as follow-up work if the candidate survives the first gate.

## Predeclared translation-quality rubric

Score each applicable criterion per fixture as:

- `0` — incorrect or materially harmful to meaning;
- `1` — partially acceptable but noticeably flawed;
- `2` — acceptable for the intended chat translation.

Criteria:

| Criterion | Minimum | Gate |
| --- | ---: | --- |
| Meaning preservation | 2 | hard |
| Pronouns and omitted subjects | 1 | review |
| Family/kinship relationships | 1 | review |
| Slang, particles, humor, and tone | 1 | review |
| Polish grammar/naturalness | 1 | review |
| No hallucinated facts/speakers/relationships | 2 | hard |
| Quoted/reply/reference handling | 1 | review |

A candidate that fails a hard gate on a representative applicable fixture cannot be accepted solely because its average score or performance is good. Human quality review remains separate from execution success and non-empty output.

## Physical-device run sequence for #109

1. **Record the environment before inference.** Capture source revision, device model, iOS version/build, Xcode version/build, SDK version, signing/provisioning state, cable/transport state, battery level/charging state, and initial thermal state.
2. **Verify compatibility.** Build/install/launch the diagnostic path on the physical iPhone. A Simulator build or previous successful app launch is not sufficient evidence for the current benchmark revision.
3. **Provision outside inference.** Transfer the exact pinned model snapshot to the diagnostic app/container without enabling a downloader in inference. Record whether verification succeeds and how provisioning was performed. Do not commit model weights.
4. **Cold run.** Start with no loaded model container. Run the source-controlled unencoded P0.1 corpus and preserve which first case incurred the cold load.
5. **Warm cases.** Continue the same pass with the loaded container and fresh sessions. Run all source-controlled context windows 0/3/8/16 without changing the fixture corpus.
6. **Cancellation.** Start a bounded generation and cancel it during execution. Record whether the task terminates as cancellation without continuing hidden generation indefinitely.
7. **Offline verification.** Disable network access after provisioning, relaunch the diagnostic path, and rerun at least one representative Indonesian -> Polish case. Any attempted hidden download is a failure.
8. **Memory.** Capture peak resident memory with a named Xcode/Instruments/device measurement source. Do not substitute model-file byte size for peak memory.
9. **Thermals and battery.** Record thermal state during/after the full pass and battery observation after the pass. Do not extrapolate a long-term energy claim from one short run.
10. **Export and review.** Preserve the deterministic benchmark JSON/Markdown plus device evidence and manually score outputs against the rubric above. Use synthetic fixtures only; do not include real WhatsApp messages or account/session data.
11. **Decision.** Commit an explicit `accept`, `reject`, or `continue-evaluation` decision with the evidence that drove it. Keep parent #4 open unless all of its own acceptance criteria are met.

## Required report fields

The physical evidence package must identify, at minimum:

- exact source revision;
- device model and OS version/build;
- Xcode version/build and SDK;
- exact model/tokenizer/chat-template revision and quantization;
- provisioning state and offline-after-provisioning result;
- cancellation result;
- cold-load, first-token, generation, token-count, throughput, and stop-reason measurements where execution completed;
- peak-memory value and named measurement source;
- thermal and battery observations;
- raw synthetic benchmark output needed for quality review;
- per-fixture human quality scores/notes;
- final candidate decision.

Until those fields come from an actual iPhone run, physical-device acceptance remains pending.
