Parent issue: #3

## Purpose

This benchmark decides whether Apple's on-device `SystemLanguageModel` is viable for contextual Indonesian -> Polish WhatsApp translation.

The benchmark intentionally separates three failure modes:

1. **Model availability failure** — the system model is unavailable on the test device or region/account state.
2. **Unsupported-language/runtime failure** — the API rejects Indonesian, Polish, mixed-language, or contextual prompts.
3. **Poor translation quality** — the route runs but the output is not good enough for the product.

## How to run

1. Open `native-ios/WhatsAppTranslator.xcodeproj` in Xcode.
2. Select the `WhatsAppTranslator` target.
3. Select a physical Apple-Intelligence-capable iPhone.
4. Build and run the app.
5. Open **P0.1 SystemLanguageModel Benchmark** from the diagnostics screen.
6. Tap **Run P0.1 benchmark**.
7. Tap **Copy all results** and archive the unedited export under `docs/native/results/` with its timestamp. Link it from this document; do not overwrite earlier runs.
8. Review output quality manually and choose a decision below.

Do not close P0.1 from simulator-only results.

There were **7 runtime errors and 4 API returns**. Of the ten Indonesian-input
cases, **zero produced a usable translation**: seven failed at runtime and
three returned unusable text. These are counts for this small fixture run,
not population-level accuracy estimates.

Every runtime error was `unsupportedLanguageOrLocale` with the description
`Unsupported language.` Model availability was not the blocker. The 4-33 ms
error latencies measure failed requests, not fast translation. The four API
returns are single observations, not cold/warm averages or throughput data.
No memory, thermal, battery, or offline measurements were included.

## Simulator control result (not a physical-device decision)

Observed on the iPhone 17 Pro simulator, iOS 26.5 (Build 23F77), with the
model available, a 4096-token context, and 23 advertised languages. Neither
`id_ID` nor `pl_PL` was advertised.

- Raw Indonesian -> English, raw Indonesian -> Polish, all contextual
  Indonesian -> Polish cases, and the English-only prompt control failed with
  `unsupportedLanguageOrLocale` / `Unsupported language.`
- English -> Polish succeeded with a natural Polish translation.
- The ASCII/Base64 envelope avoided the immediate language error, but the model
  returned unrelated fabricated JSON instead of decoding the payload.
- The full ASCII/Unicode-escape envelope hit `exceededContextWindowSize` at
  4,091 tokens out of the 4,096-token limit on the latest run.
- The smaller body-only ASCII/Unicode-escape experiment avoided the context
  overflow, but returned only an empty code-fence fragment ("``` ``` ```"),
  not a Polish translation.
- The separate iOS `Translation` framework probe reported the `id -> pl` pair
  as `unsupported` on the same simulator, so it did not provide a local
  fallback either.

These routes are therefore diagnostic experiments only; they are not a general
Indonesian fallback and must not be enabled in the product translator.

## Manual quality notes

The following is the reporting agent's qualitative review, not an owner-filled
rubric or an independent bilingual evaluation. Source-text comparisons use the
correspondingly named fixtures at the documentation baseline above because the
export does not include source texts or the installed app's commit.

- Indonesian -> English: **runtime unavailable for this request**, 33 ms.
  No output exists to judge semantic accuracy or fluency. This also blocks a
  two-hop pipeline that uses this same model for the Indonesian -> English hop.
- English -> Polish: **API success, quality defects**, 2197 ms. Output is
  understandable Polish, but the reference fixture's `too lazy` becomes
  `zbyt zmęczona` (too tired), changing the reason for not going out. The phrase
  `nie zmuszaj ją` is also grammatically defective; reviewer alternatives are
  `nie zmuszaj jej` or, closer to `don't push her`, `nie naciskaj na nią`.
  The archived model output is not corrected. One Polish response despite a
  negative locale advertisement does not establish dependable pair support.
- Indonesian -> Polish: **runtime unavailable for this request**, 8 ms.
  There is no evidence of a working direct path on this run.
- English prompt: Indonesian -> Polish: **runtime unavailable for this
  request**, 6 ms. English task framing did not make the Indonesian input work.
- ASCII/Base64 prompt: Indonesian -> Polish: **API success, translation
  failure**, 6740 ms. The output invents English assistant/student/teacher
  exchanges, quoted turns, and a summary rather than translating the target.
  Returning without an API error is not evidence of correct Base64 decoding.
- ASCII/Unicode-escape prompt: Indonesian -> Polish: **API success,
  translation failure**, 2587 ms. The English flat-tire apology is unrelated
  to the corresponding fixture and is not Polish. This device export does
  not contain the context-window error recorded in the historical simulator
  run; the two observations must remain separate.
- ASCII/Unicode-escape body prompt: Indonesian -> Polish: **API success,
  translation failure**, 949 ms. The returned text is an English refusal.
  Its underlying cause is not diagnosed by the export; no API error or
  specific guardrail reason is inferred.
- Contextual Indonesian -> Polish, 0 messages: **runtime unavailable**, 5 ms.
- Contextual Indonesian -> Polish, 3 messages: **runtime unavailable**, 4 ms.
- Contextual Indonesian -> Polish, 8 messages: **runtime unavailable**, 4 ms.
- Contextual Indonesian -> Polish, 16 messages: **runtime unavailable**, 7 ms.
  None of these four cases provides output for judging pronouns, speaker
  resolution, slang, or the quality benefit of a larger context window.

No Apple Translation framework probe result was included in this device
export. The earlier simulator-only observation above is not promoted to
physical-device evidence for that separate framework.

## Decision

- [ ] Apple SystemLanguageModel is viable as the primary translator.
- [ ] Apple SystemLanguageModel is partially viable and needs fallback.
- [x] Apple SystemLanguageModel is rejected for this product direction.

**Scope of rejection:** the required direct/contextual Indonesian -> Polish
product route on the reported runtime/configuration, not every Foundation
Models task, every language pair, or all future OS/model versions.

The required Indonesian input did not yield usable translation in any of the
ten applicable cases. Direct and contextual prompts were rejected at runtime;
encoded envelopes returned wrong content or a refusal. The English -> Polish
control does not rescue an end-to-end route whose Indonesian input fails.
For that reason, "partially viable" would misrepresent viability for the
required product path, even though the model can return Polish in one control.

### Consequences and remaining gates

This decision meets the rejection trigger for #4: evaluate a separate local
multilingual model using the same fixtures and bounded context windows.
It does not select or approve any production model/runtime, add dependencies,
change routing code, or authorize a cloud translation service. Qwen's
[archived macOS smoke experiment](qwen3-mlx-smoke-results.md) remains only
loading/non-empty-generation evidence, not translation-quality validation.

Do not enable the encoded-prompt experiments as a product workaround or
continue them as the default route. Any later reconsideration of the Apple
model needs new, versioned runtime and quality evidence. A successful future
Indonesian -> English provider plus an independently validated English ->
Polish engine could be evaluated separately; this run does not prove it.
